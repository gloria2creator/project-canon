# 规则采用与迁移闸门

## 四类授权不可互相替代

| 授权 | 允许做什么 | 不允许据此推断 |
| --- | --- | --- |
| 采用治理规则 | 按本地 README 的职责、命名和流程工作 | 旧材料中的结论已经确认 |
| 确认内容结论 | 将指定结论写入当前方案或 Decision | 当前实现、测试或真实使用已经完成 |
| 采用 Gate 或状态 | 建立指定当前入口并记录状态 | 可以创建未讨论的 Change 或补写历史状态 |
| 文件处置授权 | 按用户选择的保守整理或迁移归档方案处理 Preview 中列出的路径 | 可以处理未列入范围的文件、删除临时文件或修改归档原件 |

“开始执行”“按 README 整理”通常足以采用规则并开始扫描。若本地规则或用户此前已明确指定默认采用迁移归档，可沿用该处置方案；具体结论、状态以及未被规则清楚覆盖的文件范围仍需在 Preview 中确认。

## 先选择文件处置方案

在 Preview 中并列提供：

### 方案 A：保守整理

- 建立或更新当前方案、Decision、Change、Delivery 和来源映射。
- 原材料保留在原路径，不移动、不复制、不删除。
- 来源索引记录原路径以及后续建议。
- 适合用户只想建立权威入口、项目正在频繁开发或移动风险较高的情况。

### 方案 B：迁移归档

- 完成内容吸收和来源映射后，将已处理材料移动到项目指定归档位置。
- 清理散落的旧方案、历史报告和已完成计划，使工作区只保留当前入口和仍需维护的材料。
- 适合用户明确提出“整理并归档”“把处理完的文件移走”或希望清理项目文档的情况；此类请求优先推荐本方案。
- Preview 必须说明按文件移动，还是整体移动一个已枚举内容的目录。

用户选择一次后，本批次沿用该方案；出现新增文件、混合目录或范围变化时，只补充确认变化部分。

## 迁移前建立固定清单

写入前记录：

```text
扫描时间：
规则入口及哈希：
候选文件路径、类型、大小、修改时间或哈希：
当前 Git 状态：
拟写入结论及确认依据：
拟新建或修改文件：
拟移动或归档文件：
明确不动的代码、运行资产和用户改动：
```

长时间扫描、多人或多 Agent 协作后，重新检查清单。新增、消失或变化的文件不自动进入本批次；先报告快照变化。

批量摘要和子任务输出只用于提取候选，不是确认凭证。主执行者必须复核：

- 写入当前方案和 Decision 的每条关键结论；
- 当前 Gate、实现状态和测试数字；
- 每个来源是否完整阅读；
- 每个归档项是否满足条件并在批准清单中。

目录被建议整体归档时，还要复核它是完整来源包还是混合工作目录。来源包的判断与登记规则见 [source-intake-and-archive.md](source-intake-and-archive.md)；不能只因目录中包含一份已吸收的 Markdown，就把其余文件一并视为已处理。

## 迁移归档的两阶段执行

第一阶段只建立新结构：

1. 写入已确认的目标、Decision、Change、Delivery 和来源映射。
2. 保留所有原文件。
3. 验证新入口、双向追溯、链接、状态分离和来源覆盖。
4. 输出实际写入结果与最终归档清单。

第二阶段才处置来源：

1. 确认迁移归档方案及其文件或目录范围。
2. 检查源文件自 Preview 后未变化。
3. 逐项移动，保留原目录层级。
4. 每批后核对源、目标和哈希。
5. 任一项失败即停止该批，报告部分结果。

不得为保持“整理完成”而静默扩大操作、复制受保护文件、删除临时产物或编辑归档原件。

## 本地规则与 Skill 的关系

本地规则决定目录、命名、状态和确认主体；本 Skill 提供安全执行方法。两者拓扑不同时，适配 Skill 的输出位置，不要因本地目录与示例结构不同而放弃 Preview、确认、快照、追溯和归档闸门。
