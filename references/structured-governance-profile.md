# 结构化治理参考

仅在项目确有长期、多阶段、正式变更和证据追溯需求时采用。项目本地入口文件始终拥有具体结构的解释权。

## 参考结构

```text
<canon-root>/
├─ README.md
├─ current/
├─ changes/
├─ delivery/
├─ decisions/
└─ evidence/
```

职责：

- `README.md`：项目采用的结构、阅读顺序、命名、确认主体和特例。
- `current/`：当前已确认的产品、体验和技术目标。
- `changes/`：尚未收敛的大纲与已获准的正式变更。
- `delivery/`：当前工作入口、实现进度、验证事实和阻塞。
- `decisions/`：重要取舍、替代关系和重新评估条件。
- `evidence/`：来源映射和不适合内嵌的大型验证附件。

不要为了匹配参考结构迁移一个已经清晰的项目。

## 当前方案拆分

按长期稳定职责拆分，而不是按页面、模块、日期或单次变更拆分。产品型系统可以参考：

```text
current/
├─ 产品与领域基线.md
├─ 体验与交互基线.md
└─ 技术基线.md
```

没有用户界面的库可以省略体验文件；不含 AI 的项目不要预留 AI 章节。文件变长本身不是拆分理由。

## 标识与状态

项目需要稳定追溯时，可以为 Decision 和 Change 使用只增不复用的编号。不要在已有项目中引入第二套编号。

状态值由项目 README 定义，并满足：

- 候选、已接受、已否决、已替代可以区分；
- Change 已接受不等于实现完成；
- 实现完成不等于验证通过；
- 历史证据不能支撑新的完成声明。

可以用三轴记录可交付能力：

| 状态轴 | 示例值 |
| --- | --- |
| 设计 | 候选 / 讨论中 / 已接受 / 已替代 |
| 实现 | 未开始 / 开发中 / 部分实现 / 已实现 |
| 验证 | 未验证 / 局部验证 / 端到端验证 / 真实使用验证 / 出现反例 |

这些是示例，不是必须复制的枚举。沿用项目已定义的等价状态。

## 当前执行入口

指定唯一的当前交付入口，由它链接活跃 Change、实施文件和新鲜验证。不要根据文件名排序、修改时间或最大编号推断当前工作。

## 迁移规则

采用结构化治理时：

1. 先扫描并建立旧文件到新职责的映射。
2. 输出文件级 Preview。
3. 用户确认后，先复制或原地提取稳定事实，再验证链接。
4. 当前入口可用后，才归档旧材料。
5. 保留原路径、归档路径和吸收位置的映射。
6. 迁移必须可重复运行且不生成重复条目。
