# 审计与接续

## 验证权威候选

不要因文件名是 README、修改时间最新或正文写着“当前生效”，就直接把它当作项目权威。至少检查：

- 声明的目录、文件和 Markdown 链接是否存在；
- 项目名称、对象、技术栈和术语是否与当前仓库一致；
- 文件是否处于未完成脚手架、模板、外来复制或批量生成摘要中；
- 是否存在用户确认、项目规则引用、稳定入口链接或持续维护记录；
- 版本控制状态是否表明它只是未跟踪候选。

只有治理规则、没有它声明的主体文件时，把它标记为“治理候选或未完成采用”，不要按其阅读顺序继续。批量生成的结构化摘要默认是审阅候选，不因它使用“当前已确认”等标题就获得确认状态。

## 保持快照一致

在活跃或并发工作区：

1. 记录关键入口和状态文件的修改时间、大小或哈希。
2. 完成长文阅读和代码检查后重新比较。
3. 文件在审计期间变化时，丢弃旧内容形成的结论，重新读取当前版本，或明确报告本轮快照不稳定。
4. 不把并发生成的新文件自动提升为权威，也不干预其他执行者。

## 恢复阅读顺序

根据项目实际结构解析路径，不硬编码文件名：

1. 项目指令和治理入口；
2. 当前已确认方案；
3. 当前交付或状态入口；
4. 活跃正式变更；
5. 对应实施与验证记录；
6. 必要的 Decision 和 Evidence；
7. 相关代码、版本控制状态、运行入口和新鲜测试。

恢复时不根据聊天印象继续，也不重新讨论已经有明确确认凭证的决定。

## 只读审计输出

至少报告：

- 当前权威入口和各职责位置；
- 当前已确认目标；
- 当前活跃工作及其依据；
- 未确认候选；
- 文档之间的冲突、重复和孤立内容；
- 文档与新鲜代码事实的差异；
- 失效链接、状态值漂移和缺少的反向链接；
- 证据的新鲜度及其不能证明的内容；
- 建议操作的文件级 Preview。

不要在审计请求中顺手修复。

## 状态对账

同时读取当前汇总入口和活跃工作的详细执行文件：

1. 汇总与详细状态一致时，按两者共同口径报告。
2. 详细文件有更晚检查点、汇总仍是旧状态时，把详细文件作为“最新记录的检查点”，同时明确标记汇总入口滞后；不要自行回写。
3. 两者内容冲突且无法从确认记录、时间和证据判断时，标记为权威冲突，不替项目选择。
4. 工作区存在未提交或未跟踪实现时，报告为活动工作区，不称为稳定发布基线。

按性质区分问题：

| 类型 | 含义 |
| --- | --- |
| 权威冲突 | 两个位置对同一事实给出无法兼容的结论 |
| 状态滞后 | 详细执行已有新检查点，汇总尚未同步 |
| 追溯缺口 | 结论存在，但确认来源、Decision 或反向链接缺失 |
| 格式漂移 | 状态文字、编号或模板不符合本地规则，但尚未改变事实含义 |
| 无效权威候选 | 文件声称当前生效，但本地结构、链接、术语或采用证据不支持 |
| 快照不稳定 | 关键文件在审计期间发生变化，当前结论混有不同时间点 |

## 验证口径

分别报告受影响测试、单元测试、全量回归、集成测试、构建、lint、真实 Provider、浏览器和真实使用。任一必需检查仍为非零退出或未执行时，不把整个 Gate 描述为全绿。

“与本批无直接因果”可以说明失败归属，但失败仍是当前工作区事实；只有项目规则明确允许带已知失败关闭，并留下例外确认时，才不阻塞最终 Gate。

## 完成检查

- 权威位置唯一；
- 当前方案、Decision、Change、Delivery 和 Evidence 能按需双向追溯；
- 设计、实现、验证状态分离；
- 当前执行入口指向真实活跃工作；
- 文件路径、Markdown 链接和文字章节引用有效；
- 来源满足归档条件；
- 正式编号没有重复或复用；
- 同一流程再次执行不会重复写入；
- 完成声明基于本轮重新读取和必要的新鲜验证。

## 进行中工作增量记录

Bug 排查、返工、迁移和验收等持续工作，在项目已有 Delivery 或交付入口维护同一条记录，从发现问题一直更新到解决、验证和关闭。原始聊天保留为来源，不把每轮对话复制成开发日志。

交付记录同时保留两层信息：

- 当前快照：只反映最新的已确认事实、待核验问题、授权边界、当前状态和下一步。
- 关键检查点：按时间追加有状态意义的变化，使被推翻的假设、阶段结论和授权变化仍可追溯。

以下变化触发检查点：

- 新事实被代码、数据、测试或真实使用确认，或旧假设被推翻；
- 用户确认可识别的决定，或授权从只读变为允许实施；
- 代码、接口、配置或数据发生实际变化；
- 出现新的验证结果、阻塞、回滚、交接或关闭条件。

重复解释、临时猜测和普通确认用语不单独记录。只有“同意、可以、ok”等回复紧跟可识别的确认对象时，才把它作为确认凭证。

按修复性质路由：

- 只是恢复已经确认的行为：在同一 Delivery 中记录根因、修复、影响范围和验证，不必新建 Change。
- 改变目标方案、正式实施范围、数据或接口契约：更新或建立 Change；重要取舍进入 Decision；已确认目标发生变化时再更新当前方案。
- 只是临时绕过或尚未完成必要验证：标记为缓解中或待验证，不写成已解决。

关闭记录至少说明根因、实际修复、涉及范围、新鲜验证、遗留限制和最终状态。关闭前仍缺少必需检查时，保持打开状态。

## 接续记录

持续更新项目已有交付入口，至少保留：

```text
当前工作或 Gate：
来源或问题记录：
当前快照：
已经完成：
新鲜验证证据：
未完成、偏差或阻塞：
本阶段确认的决定与非目标：
涉及的文件、接口或数据变化：
关键检查点：
问题解决与关闭：
下一步：
当前代码基准或工作区注意事项：
```

不要为了交接另建平行进度报告，除非现有入口无法承载且用户确认新增。
