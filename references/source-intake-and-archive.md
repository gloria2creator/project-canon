# 来源吸收与安全归档

## 标准流程

```text
登记来源
→ 完整阅读
→ 区分说话者和内容性质
→ 对照当前方案、Decision、候选与 Change
→ 输出写入 Preview
→ 用户确认
→ 分别写入权威位置
→ 更新来源映射和处理状态
→ 执行已确认的归档
```

原始来源保持只读。审阅文件只保存提取、映射、冲突和限制，不复制整份原文。

## 内容分类

至少区分：

- 用户明确确认的决定；
- 用户仍在讨论的想法；
- AI、技术人员或他人的建议；
- 外部资料声称的事实；
- 代码、测试和真实使用证据。

外部事实可能变化时，使用前重新核验；未核验内容标记为需核验，不支撑正式结论。

## Preview 分类

| 分类 | 判定 | 默认处理 |
| --- | --- | --- |
| 已覆盖 | 当前权威已有相同结论 | 只建立来源映射 |
| 可吸收 | 已确认且当前权威确有缺失 | 确认后原地补入 |
| 冲突 | 与当前方案或已接受 Decision 不一致 | 不覆盖，列出裁决问题 |
| 候选 | 有价值但尚未确认 | 进入候选或提案位置 |
| 需核验 | 外部事实或实现判断缺乏新鲜证据 | 留在来源记录 |
| 无长期价值 | 重复、闲聊、临时想法或已被完整替代 | 不进入长期事实 |

Preview 必须列出具体目标文件和操作类型。把“修改内容”和“移动或归档文件”分开呈现。

## 归档条件

满足以下条件后才归档来源：

1. 已完整阅读相关内容。
2. 稳定结论、未解决问题、独有背景和需核验事实已分别提取。
3. 每项保留内容已有后续位置或处理入口。
4. 来源映射记录原路径、归档路径、处理状态和吸收位置。
5. 用户已经确认 Preview 中的归档操作。

问题尚未最终裁决并不阻止归档，但必须已有候选或 Decision 入口。

## 归档操作边界

- 用户选择保守整理时，只登记来源映射，不移动原文件。
- 用户选择迁移归档时，Preview 列出源路径、目标路径和操作类型。可以逐文件移动，也可以整体移动用户明确批准且内容已枚举的目录。
- 目录混有代码、网页、脚本、字体、图片、数据库、测试数据或运行配置时，先区分哪些属于本次材料或证据。只移动已确认范围；如果用户明确把整个目录作为历史材料归档，则可以整体移动。
- 不按文件扩展名直接判定归档位置。代码形态的文件可能是当前实现、可运行原型、历史设计输出、验收附件或来源包依赖；先判断它在项目中的实际职责。
- 归档是移动原件，不是顺带重构目录。先创建目标父目录并校验冲突，再逐项移动。
- 移动被拒绝、目标冲突或部分成功时立即停止该批次，输出已完成与未完成清单。不得自行把移动改成复制，也不得用删除源文件补齐结果。
- 归档原件保持字节不变。因路径变化导致链接失效时，在来源索引记录限制，或在获得用户明确许可后生成修复副本；不要直接编辑原件。
- 临时摘要、扫描清单和校验脚本也属于文件操作范围。除非用户明确授权删除，否则放在工作区外的临时目录，或保留并报告。

## 整体来源包

一个目录只有同时满足以下条件，才作为整体来源包归档：

1. 目录内文件共同构成一个可识别的历史方案、静态原型、设计交付物或验证附件包。
2. 已检查项目运行入口、构建配置、脚本引用、Markdown 链接和文本路径引用，未发现它仍承担当前运行职责；存在引用时先判断应更新、保留还是阻止归档。
3. 已记录当前实现或后继材料；没有替代关系时，不得仅因存在另一个同类目录就推断它已废弃。
4. 已枚举目录内容及类型，并区分主体、附件、依赖和无关文件。
5. Preview 明确请求整体移动该目录，而不只是处理其中某一份文档。

来源映射把整个包作为一项登记，至少记录：

```text
原目录：
归档目录：
来源包性质：
主体文件：
随包附件或依赖：
当前引用检查：
替代关系或历史边界：
支持的结论：
被使用位置：
不能证明什么：
处理状态：
```

实际移动范围必须与登记范围一致：

- 只登记某一文件时，只能移动该文件。
- 整体移动目录时，必须登记整个来源包，不能只登记其中的 README 或 Markdown。
- 目录中发现未登记的当前实现或无关资产时，将其排除或重新请求范围确认。

## 删除条件

默认不删除。只有用户明确要求删除，并确认不存在独有信息、追溯价值、合规或保留要求时才删除。删除前重新验证吸收位置和备份边界。

## 与批量文档整理的边界

本流程适合围绕当前项目事实吸收有限来源。面对大量历史文件的一次性逐份审阅和集中归档，应使用专门的文档清理流程；完成后再把稳定结论写回项目 Canon。
